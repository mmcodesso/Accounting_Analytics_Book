## Purpose and learning outcomes

The auditor wants one query that tests whether the model agrees with the control totals of Parts II and III, can be run again after every change, and reports a pass or a fail for each test. It is the Power BI counterpart of Chapter 12's audit library. The exercise also asks what a test library cannot do, which is the judgment that separates a control from a comfort. The analytics type is diagnostic, with a first step toward monitoring.

Students can:

- turn control totals from earlier chapters into expected values of a repeatable query (Requirement 1);
- explain a difference between two totals and test it as its own expected difference (Requirement 2);
- predict and observe which tests catch a change in the model (Requirement 3);
- say what a passing library shows, what it does not, and when to run it (Requirement 4).

**Competencies practiced.** CPA Evolution Core S2 M9 (audit procedures, analytical procedures and audit data analytics) and ISC M4 (use and management of data); IMA Data Analytics and Insights (data governance) and Reporting and Control (internal control); IFAC IES 2 (f) (audit) and IES 2 (i) (judging the adequacy of information and communications technology processes and controls); AACSB A5 part 5.1.

## Step-by-step solution

### Requirement (1): The query and its seven tests

**Step 1. Build the tab.**

a. In **DAX query view**, open a new query tab and rename it `Control Totals`.
b. Type the query from the exercise. Replace the two expected values of 0 with Chapter 6's invoice lines and revenue.
c. Add one `ROW` for each of the other four tests the exercise names, and the one of Requirement 2.
d. Select the query and choose **Run**.

The model answer's query, with its seven tests:

```dax
// Control totals: each test must agree within one cent
EVALUATE
VAR Tests =
    UNION (
        ROW ( "Test", "Invoice lines, fiscal 2026", "Expected", 9522,
            "Actual", CALCULATE ( [Invoice Lines], 'Date'[Year] = 2026 ) ),
        ROW ( "Test", "Revenue, fiscal 2026", "Expected", 29756420.08,
            "Actual", CALCULATE ( [Revenue], 'Date'[Year] = 2026 ) ),
        ROW ( "Test", "Net income, fiscal 2026", "Expected", 4503611.24,
            "Actual", CALCULATE ( [Net Income], 'Date'[Year] = 2026 ) ),
        ROW ( "Test", "Journal entry debits, all years", "Expected", 129860610.27,
            "Actual", CALCULATE ( SUM ( GLEntry[Debit] ), GLEntry[SourceDocumentType] = "JournalEntry" ) ),
        ROW ( "Test", "Manufacturing variance (5080), fiscal 2026", "Expected", 2265636.88,
            "Actual", CALCULATE ( [GL Amount], Account[AccountNumber] = 5080, 'Date'[Year] = 2026 ) ),
        ROW ( "Test", "Invoice revenue in the ledger, fiscal 2026", "Expected", 29761002.45,
            "Actual", CALCULATE ( - [GL Amount], GLEntry[SourceDocumentType] = "SalesInvoice",
                Account[AccountNumber] IN { 4010, 4020, 4030, 4040, 4080 }, 'Date'[Year] = 2026 ) ),
        ROW ( "Test", "Ledger less invoice lines = SI-2026-013741 to 013743", "Expected", 4582.37,
            "Actual", CALCULATE ( - [GL Amount], GLEntry[SourceDocumentType] = "SalesInvoice",
                Account[AccountNumber] IN { 4010, 4020, 4030, 4040, 4080 }, 'Date'[Year] = 2026 )
                - CALCULATE ( [Revenue], 'Date'[Year] = 2026 ) )
    )
RETURN
    ADDCOLUMNS (
        Tests,
        "Difference", ROUND ( [Actual] - [Expected], 2 ),
        "Result", IF ( ABS ( [Actual] - [Expected] ) <= 0.01, "Pass", "Fail" )
    )
```

**Check:** seven rows, each Pass, with a Difference of zero.

| Test | Expected |
|---|---:|
| Invoice lines, fiscal 2026 | 9,522 |
| Revenue, fiscal 2026 | $29,756,420.08 |
| Net income, fiscal 2026 | $4,503,611.24, the transfer of JE-2026-000297 |
| Journal entry debits, all years | $129,860,610.27 |
| Manufacturing variance, 5080 | $2,265,636.88 |
| Invoice revenue in the ledger | $29,761,002.45 |
| The reconciling item | $4,582.37 |

**Watch for:** an expected value left at 0. The test then fails with a Difference equal to its Actual, and the student concludes that the model is broken. The expected values are the point of the exercise. A value typed rounded to the dollar fails too, because the tolerance is one cent.

### Requirement (2): The difference

**Step 2. Explain it and test it.** The ledger's invoice revenue exceeds the invoice lines' by $4,582.37. The cause is SI-2026-013741 to 013743, with amounts of $1,112.23 and $3,233.18 and $236.96: they are dated in late 2025 and posted on 2026-01-01 (Chapter 6, Exercise 6.1). The model answer adds the difference as a test of its own, with the documented total as the expected value, so the library reports it as a reconciling item and not as a failure.

**Check:** the seventh row reads Pass. **Watch for:** two traps in the tests of this step.

- A journal entry debit total written with GL Amount. It reads $0.00, because the entries balance. The same total written with SUM of Debit and the closing flag left out reads $28,048,356.69, $101,812,253.58 short, the debits of the closes.
- An invoice revenue test over every Revenue account. It reads $29,975,619.11, $214,616.66 above the item groups' accounts, which is the freight the sales invoices also post. Name the accounts.

### Requirement (3): Keep the closes

**Step 3. Change GL Amount, run, undo, run.**

a. In **Report view**, select GL Amount in the **Data** pane and change its formula in the formula bar so that it no longer leaves out the closing entries.
b. Rerun the tab and record which tests fail.
c. Undo the change and rerun.

```dax
GL Amount =
CALCULATE (
    SUM ( GLEntry[Debit] ) - SUM ( GLEntry[Credit] ),
    GLEntry[IsYearEndClose] = FALSE ()
)
```

**Check:** two tests fail, the net income and the manufacturing variance, both reading 0, because with the closes kept each year's revenue and expense net to zero. The other five pass: the invoice lines and the revenue do not use GL Amount, the debit total uses SUM, the invoice revenue in the ledger is posted by sales invoices that no close touches, and the reconciling item is a difference of those. Test 3 of the Tests tab passes as well, because it leaves out the two closes by VoucherNumber. After the undo, every test passes. **Watch for:** the change left in. The Net Income card of the Income Statement page then shows zero.

### Requirement (4): The conclusion

**Step 4. Outline it.** The passing tests show that the model's totals agree with earlier, independent calculations on the same database. They cannot show that individual rows are right, that the source data is complete or valid, or that a total no test covers is right. Run the library after every refresh and every change to the model, before the report is shared.

## What a strong answer says

- **(1)** Each expected value comes from a named earlier chapter, and the query reports Pass or Fail for each.
- **(2)** The three invoices, their dates, and why the difference is a reconciling item, not an error.
- **(3)** Which tests failed and why, and that the passing ones do not depend on GL Amount.
- **(4)** What agreement shows and what it leaves open, and when to run the library.

A strong answer ends with the limit of the evidence. A weak one ends with "all tests pass, so the report is right".

## Common mistakes and how to respond

- **Expected values at 0.** *Symptom:* two failures in a correct model. *Response:* ask where the expected values come from.
- **A debit total from GL Amount.** *Symptom:* an Actual of $0.00. *Response:* ask what debits less credits is for a balanced entry.
- **Every revenue account.** *Symptom:* $29,975,619.11. *Response:* ask which account the freight posts to.
- **The difference left as a failure.** *Symptom:* a Fail the student explains in prose. *Response:* ask for a test that expects it.
- **The change left in.** *Symptom:* a zero Net Income card. *Response:* undo it and run the tab.
- **A conclusion of certainty.** *Symptom:* "the model is correct". *Response:* ask what a test of totals cannot see.
