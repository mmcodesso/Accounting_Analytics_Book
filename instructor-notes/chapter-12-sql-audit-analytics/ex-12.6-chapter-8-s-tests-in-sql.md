## Purpose and learning outcomes

Chapter 2 promised that the duplicate payment analysis of Exercise 2.6 would be completed in SQL, and Chapter 8 ran its tests in Excel. The chief audit executive asks for the same results in SQL, so that they run every quarter without a workbook. The audit mindset: re-performing a test in a second tool tests the test. Agreement with the workbook is evidence that both compute the same thing, and every wrong version here returns plausible numbers, so the defenses are a known answer and a positive control. The analytics type is diagnostic.

Students can:

- find duplicates with GROUP BY and HAVING, exact and standardized (Requirements 1 and 2);
- find near-duplicates with a self-join that lists each pair once (Requirement 3);
- test document series with SUBSTR, CAST and LAG, partitioned correctly (Requirement 4);
- compute a first-digit deviation with `printf` and `LOG10` and reproduce the workbook (Requirement 5);
- record results and dispositions and explain what SQL adds (Requirement 6).

## Step-by-step solution

### Requirement (1): Duplicate supplier invoices

**Step 1. Find the repeated numbers, exact and standardized.** A Repeated CTE groups by SupplierID and InvoiceNumber with `HAVING COUNT(*) > 1`; the final query lists both invoices of each pair with their payments.

```sql
-- Exercise 12.6, test D1: supplier invoice numbers that appear more than once for a supplier
-- Population: all supplier invoices; expected: no rows
WITH Repeated AS (
    SELECT SupplierID, InvoiceNumber
    FROM PurchaseInvoice
    GROUP BY SupplierID, InvoiceNumber
    HAVING COUNT(*) > 1
)
SELECT pi.SupplierID, pi.InvoiceNumber, pi.PurchaseInvoiceID,
    pi.InvoiceDate, ROUND(pi.GrandTotal, 2) AS GrandTotal,
    COUNT(dp.DisbursementID) AS Payments,
    ROUND(SUM(dp.Amount), 2) AS AmountPaid
FROM PurchaseInvoice AS pi
    INNER JOIN Repeated AS r ON r.SupplierID = pi.SupplierID
        AND r.InvoiceNumber = pi.InvoiceNumber
    LEFT JOIN DisbursementPayment AS dp
        ON dp.PurchaseInvoiceID = pi.PurchaseInvoiceID
GROUP BY pi.PurchaseInvoiceID, pi.SupplierID, pi.InvoiceNumber,
    pi.InvoiceDate, pi.GrandTotal
ORDER BY pi.SupplierID, pi.InvoiceNumber, pi.PurchaseInvoiceID;
```

The standardized test (D2) groups by supplier and `UPPER(TRIM(REPLACE(REPLACE(InvoiceNumber, '-', ''), ' ', '')))` and compares `COUNT(*)` with `COUNT(DISTINCT InvoiceNumber)`.

**Check:** D1 returns 12 rows, two for each of six pairs, each invoice paid once; D2 returns 6 rows with one exact spelling each, the same six groups as D1 and none new. **Watch for:** grouping by InvoiceNumber alone returns the same rows here, because every number carries its supplier's code; it passes on this data and is wrong on other data.

### Requirement (2): Repeated check numbers

**Step 2. Group the payments by supplier and check number.**

```sql
-- Exercise 12.6, test D3: check numbers used more than once for the same supplier
-- Population: payments with a check number; expected: no rows
SELECT SupplierID, CheckNumber, COUNT(*) AS Payments,
    ROUND(SUM(Amount), 2) AS Amount
FROM DisbursementPayment
WHERE CheckNumber IS NOT NULL
GROUP BY SupplierID, CheckNumber
HAVING COUNT(*) > 1
ORDER BY CheckNumber;
```

**Check:** 2 rows: CHK0006076 and CHK0019708, each used twice for supplier 1. ACH and wire payments carry no check number, so they need a separate payment-reference test. **Watch for:** without the filter the query returns 105 rows, because the ACH and wire payments, with no check number, form a group of their own for each supplier.

### Requirement (3): Near-duplicate payments

**Step 3. Join the payments to themselves.** The ID condition keeps each pair once; the date conditions keep different dates within 30 days.

```sql
-- Exercise 12.6, test D4: payments to a supplier for the same amount within 30 days
-- Population: supplier payments dated through 2026-12-31; expected: no rows
SELECT a.SupplierID, a.Amount, a.PaymentNumber, a.PaymentDate,
    b.PaymentNumber AS OtherPayment, b.PaymentDate AS OtherDate,
    ABS(julianday(b.PaymentDate) - julianday(a.PaymentDate))
        AS DaysApart,
    CASE WHEN a.PurchaseInvoiceID = b.PurchaseInvoiceID
        THEN 1 ELSE 0 END AS SameInvoice
FROM DisbursementPayment AS a
    INNER JOIN DisbursementPayment AS b
        ON b.SupplierID = a.SupplierID AND b.Amount = a.Amount
        AND b.DisbursementID > a.DisbursementID
WHERE a.PaymentDate <> b.PaymentDate
    AND a.PaymentDate <= '2026-12-31' AND b.PaymentDate <= '2026-12-31'
    AND ABS(julianday(b.PaymentDate) - julianday(a.PaymentDate)) <= 30
ORDER BY DaysApart, a.SupplierID;
```

**Check:** 13 rows, none with SameInvoice equal to 1. Test D5 counts every pair: 113 pairs, 13 within 30 days, 0 on the same invoice; 6 are within 14 days, the chapter's example. **Watch for:** the condition on the IDs is the one that matters.

- Without `b.DisbursementID > a.DisbursementID`, or with `<>` in its place, every pair is listed twice: 26 rows, and 226 pairs in test D5.
- With neither the ID nor the date condition, test D5 reports 40,090 "pairs", 39,864 of them a payment paired with itself.
- Leaving out ABS, or the condition on the dates, changes no row on this data. Count the rows with and without before trusting either.

### Requirement (4): Document series

**Step 4. Take the year and the sequence from each number.** A Numbers CTE stacks the four series with UNION ALL, extracting year and sequence with SUBSTR and CAST; the final query gives the first and last number of each year.

```sql
WITH Numbers AS (
    SELECT 'Sales invoice' AS Series,
        CAST(SUBSTR(InvoiceNumber, 4, 4) AS INTEGER) AS NumberYear,
        CAST(SUBSTR(InvoiceNumber, 9) AS INTEGER) AS Sequence
    FROM SalesInvoice
    UNION ALL
    SELECT 'Purchase order', CAST(SUBSTR(PONumber, 4, 4) AS INTEGER),
        CAST(SUBSTR(PONumber, 9) AS INTEGER)
    FROM PurchaseOrder
    UNION ALL
    SELECT 'Cash receipt', CAST(SUBSTR(ReceiptNumber, 4, 4) AS INTEGER),
        CAST(SUBSTR(ReceiptNumber, 9) AS INTEGER)
    FROM CashReceipt
    UNION ALL
    SELECT 'Journal entry', CAST(SUBSTR(EntryNumber, 4, 4) AS INTEGER),
        CAST(SUBSTR(EntryNumber, 9) AS INTEGER)
    FROM JournalEntry
)
```

Test S1 returns 12 rows: the cash receipt, purchase order, and sales invoice numbers continue across years, and the journal entry numbers restart, ending at 266, 288, 297.

**Step 5. Compare each number with the one before.** LAG is partitioned by series for a series that continues, and by series and year for the one that restarts.

```sql
Steps AS (
    SELECT Series, Sequence - LAG(Sequence) OVER (
        PARTITION BY Series ORDER BY Sequence) AS Step
    FROM Numbers
    WHERE Series <> 'Journal entry'
    UNION ALL
    SELECT Series, Sequence - LAG(Sequence) OVER (
        PARTITION BY Series, NumberYear ORDER BY Sequence)
    FROM Numbers
    WHERE Series = 'Journal entry'
)
SELECT Series, COUNT(Step) AS StepsTested, MAX(Step) AS LargestStep,
    SUM(CASE WHEN Step > 1 THEN 1 ELSE 0 END) AS Gaps
FROM Steps
GROUP BY Series
ORDER BY Series;
```

**Check:** four rows, a largest step of 1 and 0 gaps in every series. **Watch for:** partitioning a continuing series by year leaves each year boundary untested: 7,408 steps become 7,406 for the cash receipts. As a positive control, take the first sales invoice of the second year out of the list: the unpartitioned test finds 1 gap and the partitioned one 0.

### Requirement (5): First digits

**Step 6. Read the first significant digit.** The digit of each payment dated by the as-of date comes from this line of a Payments CTE:

```sql
CAST(SUBSTR(printf('%.15e', dp.Amount), 1, 1) AS INTEGER) AS Digit
```

**Step 7. Compare with Benford's proportions.** A Groups CTE stacks all, full (Amount = GrandTotal) and partial payments; Observed counts the digits of each group; the final query averages the absolute deviations from the expected proportion.

```sql
Observed AS (
    SELECT PaymentGroup, Digit, COUNT(*) AS Payments,
        COUNT(*) * 1.0 / SUM(COUNT(*)) OVER (PARTITION BY PaymentGroup)
            AS Actual
    FROM Groups
    GROUP BY PaymentGroup, Digit
)
SELECT PaymentGroup, SUM(Payments) AS Payments, COUNT(*) AS Digits,
    ROUND(AVG(ABS(Actual - LOG10(1 + 1.0 / Digit))), 5) AS MAD
FROM Observed
GROUP BY PaymentGroup
ORDER BY PaymentGroup;
```

![A mock of the first-digit result for the three payment groups, the check against Tutorial 8.1.](../figures/chapter-12-sql-audit-analytics/IF-12-6-A.pdf)

Test B2 repeats the query with the nine proportions typed in a CASE and gives the same MAD.

**Check:** all payments: 39,864, 9 digits, MAD 0.01295; full payments: 34,115, 9 digits, MAD 0.00755; partial payments: 5,749, 9 digits, MAD 0.04496: the values of Tutorial 8.1. **Watch for:** three wrong versions, none an error.

- Without `PARTITION BY PaymentGroup` the deviations read 0.056, 0.064, 0.103; with `1 / Digit` in place of `1.0 / Digit` (an integer division) they read 0.084, 0.083, 0.089.
- Reading the first character of the amount makes the 121 payments below one dollar a tenth digit, 0, and the MAD of all payments reads 0.01283, close enough to pass. Only the Digits column, ten where nine belong, gives it away.

### Requirement (6): Dispositions and the note

**Step 8. Record each test.** Duplicate invoices: obtain both invoices of each pair. Standardized numbers: the same groups as D1 and no more, kept with D1 for investigation. Repeated checks: trace to the bank statement. Near-duplicates: no pair pays the same recorded invoice, but the test covers only the same supplier and amount on different dates, so review the invoices, orders and receipts of the pairs within 30 days. Series: no gaps. First digits: all nine digits appear, and the partial payments deviate, plausibly from a selection by size (Chapter 8).

The note: a near duplicate is a pair of different payments within a range of dates, so each payment is compared with the others of its supplier, which needs the table joined to itself; GROUP BY finds only identical values. Saved SQL avoids rebuilding the manual workbook analysis, but each recurring run still needs a refreshed, reconciled snapshot, an as-of date and retained results, because the query fetches no new transactions. `printf('%.15e')` makes the first character the first significant digit (0.12 reads 1.200000000000000e-01).

> **Instructor notes, Exercise 12.6:** (1) six supplier invoice numbers each appear twice for the same supplier; each pair has different amounts, and each invoice was paid once (Exercise 2.6). Standardized numbers (UPPER, TRIM, and REPLACE of hyphens and spaces) find the same six pairs and no others: the numbers are entered consistently. (2) Two check numbers are used twice, both for supplier 1: CHK0006076 and CHK0019708; ACH and wire payments carry no check number, so they need a separate payment-reference test. (3) 113 pairs share supplier and amount on different dates; 13 are within 30 days (the chapter's example, with 14 days, finds 6), and none pays the same recorded invoice, which within the test's scope (same supplier and amount, different dates) does not exclude a duplicate bill under another number, on the same date, or at another amount, so the pairs within 30 days need their invoices, orders, and receipts reviewed before they are treated as distinct purchases. (4) No gaps in any series. Sales invoices and cash receipts continue across years (SI 1-6,732 in 2024, 6,733-13,740 in 2025, 13,741-20,914 in 2026; CR 1-2,274, 2,275-4,840, 4,841-7,409), as do purchase orders (1-3,921, 3,922-10,466, 10,467-18,832); journal entries restart each year (1-266, 1-288, 1-297). A LAG partitioned by year on a continuing series would miss a gap between the last number of one year and the first of the next. (5) MAD: all payments 0.01295, full payments 0.00755, partial payments 0.04496, exactly the values of Tutorial 8.1. All nine digits occur in each group, so the average is over nine (a quarter missing a digit needs the nine listed and joined). The partial payments' nonconformity plausibly reflects a selection by size (only invoices of 1,000 or more are paid in parts), and conformity would not prove the payments genuine. printf('%.15e') writes 688.42 as 6.884200000000000e+02 and 0.12 as 1.200000000000000e-01, so the first character is the first significant digit for every positive amount (the smallest payment is 0.12); with printf's default of six decimals, an amount just below a power of ten would round up (999,999.99 to 1.000000e+06), although no payment here changes its digit. LOG10 needs SQLite's math functions, which depend on how the library was built (SELECT LOG10(10.0) returns 1 when they are present); the Windows release of DB Browser for SQLite includes them and DB Browser for SQLCipher lacks them, and a CASE that lists the nine expected proportions can replace it (test B2 of the model script).

## What a strong answer says

- **(1) to (3)** Six pairs, two checks and no pair on one recorded invoice, each with a disposition and what the test cannot show.
- **(4)** No gaps, and why the series that continues is not partitioned by year.
- **(5)** The partial payments deviate for a plausible reason Chapter 8 gives, and the answer says a first-digit result is a screen, not proof either way.
- **(6)** The note names what SQL gains, and what it does not remove: the need for a known answer to check against.

## Common mistakes and how to respond

- **A self-join without the ID condition.** *Symptom:* 26 rows. *Response:* count the rows with and without it.
- **A series partitioned by year.** *Symptom:* fewer steps, no error. *Response:* ask what the first number of a year is compared with.
- **The first character of the amount.** *Symptom:* ten digits. *Response:* ask what the first character of a payment below one dollar is.
