## Purpose and learning outcomes

Chapter 3 explained that the database declares no foreign keys, so its relationships must be tested. The audit senior wants a set of integrity tests run with anti-joins before the team relies on the joins in its other work. The exercise is the auditing counterpart of the chapter's left-join section: each requirement tests one parent-child pair, and the last asks the student to classify what was found. The analytics type is descriptive, with a diagnostic step in the classification.

By the end, students can:

- profile a table with the chapter's tests and say which results were expected (outcome 3);
- write an anti-join from a child to its parent with the right IS NULL test and the document type (outcome 2);
- find the parents that have no children, the other direction of the same test (outcome 2);
- separate a filled-in key that matches nothing from a missing key, and classify each finding as an integrity failure, a process exception or an expected condition.

**Competencies practiced.** CPA Evolution Core S2 M4 (information technology and IT controls) and BAR M10 (data models and joins); IMA Data Analytics and Insights (data governance) and Reporting and Control (internal control); IFAC IES 2 (i) and (f); AACSB A5 part 5.1.

## Before you assign

- **Data conditions.** The tests rely on conditions planted in the data: ledger rows of type PayrollPayment whose document does not exist, work orders without operations, and labor entries whose WorkOrderOperationID matches no operation. Customers without orders are all inactive. The profile shows time records ending before the year does.
- **Verify first.** `SELECT COUNT(*) FROM PayrollPayment;` returns 8,194 rows, and the ledger holds payroll postings for each of them.

## Step-by-step solution

### Requirement (1): The profile

**Step 1. Profile the labor time by labor type.**

```sql
-- Requirement (1): a profile of LaborTimeEntry by labor type
-- Population: LaborTimeEntry, every entry; expected: 3 labor types, 51,117 direct entries
SELECT LaborType, COUNT(*) AS Entries,
    COUNT(WorkOrderOperationID) AS WithOperation,
    COUNT(DISTINCT EmployeeID) AS Employees,
    MIN(WorkDate) AS FirstWorkDate,
    MAX(WorkDate) AS LastWorkDate
FROM LaborTimeEntry
GROUP BY LaborType
ORDER BY LaborType;
```

**Check:** direct 51,117 entries, 51,114 with an operation, 64 employees, 2024-01-17 to 2026-12-11; indirect 11,702, 0 with an operation, 65 employees, 2024-01-15 to 2026-12-04; non-manufacturing 6,040, 0, 12, 2024-01-01 to 2026-12-11. Expected: indirect and non-manufacturing time has no operation by design, and manufacturing time starts in the first month of the window. Not expected: three direct entries with no operation (Exercise 9.6), and an end on December 11, 2026, before the year ends. Indirect time ends a week earlier. **Watch for:** a profile describes; it does not test. Students who stop here have not yet asked which of the three are errors.

### Requirement (2): Ledger rows with no payroll payment

**Step 2. Find the ledger rows that point to no payment.**

```sql
-- Requirement (2): ledger rows that point to no payroll payment
-- Population: GLEntry, PayrollPayment; expected: six rows, three pairs of 7,971.10
SELECT gl.GLEntryID, gl.PostingDate, gl.SourceDocumentID,
    gl.Debit, gl.Credit, gl.Description
FROM GLEntry AS gl
    LEFT JOIN PayrollPayment AS pp
        ON pp.PayrollPaymentID = gl.SourceDocumentID
WHERE gl.SourceDocumentType = 'PayrollPayment'
    AND pp.PayrollPaymentID IS NULL
ORDER BY gl.GLEntryID;
```

![A mock of the ledger rows that point to no payroll payment, for the discussion of what an integrity failure looks like.](../figures/chapter-10-joining-and-summarizing/IF-10-5-A.pdf)

**Step 3. Total the rows.**

```sql
-- Requirement (2): their totals
-- Population: as above; expected: debits and credits 23,913.30 each
SELECT COUNT(*) AS Postings,
    ROUND(SUM(gl.Debit), 2) AS Debits,
    ROUND(SUM(gl.Credit), 2) AS Credits
FROM GLEntry AS gl
    LEFT JOIN PayrollPayment AS pp
        ON pp.PayrollPaymentID = gl.SourceDocumentID
WHERE gl.SourceDocumentType = 'PayrollPayment'
    AND pp.PayrollPaymentID IS NULL;
```

**Check:** six rows in 3 pairs: 7231 and 7232 (2024-01-19, SourceDocumentID 1); 12521 and 12522 (2025-01-03, SourceDocumentID 2646); 18069 and 18070 (2026-01-02, SourceDocumentID 5420). Each pair is a $7,971.10 debit, "Clear accrued payroll", and credit, "Disburse payroll cash"; the totals are $23,913.30 each side. **Watch for:** without the document type the anti-join returns 474,622 rows, every ledger row that is not a payroll payment. NOT IN returns the same 6 rows here, because the payment key is never NULL; that safety is a property of this column, not a rule. The test in the other direction, payments with no ledger rows, returns 0 of 8,194.

### Requirement (3): Customers with no orders

**Step 4. Find the customers that placed no order.**

```sql
-- Requirement (3): customers with no sales order in the database
-- Population: Customer; expected: nine customers, all inactive
SELECT c.CustomerID, c.CustomerName, c.CustomerSegment,
    c.IsActive
FROM Customer AS c
    LEFT JOIN SalesOrder AS so ON so.CustomerID = c.CustomerID
WHERE so.SalesOrderID IS NULL
ORDER BY c.CustomerID;
```

**Check:** nine customers, every one with IsActive 0, and they are all the inactive customers of the file. **Watch for:** adding `AND c.IsActive = 1` returns 0 rows; the flag is something to read in the result, not a filter.

### Requirement (4): Work orders with no operations

**Step 5. Find the work orders that have no operations.**

```sql
-- Requirement (4): work orders with no work order operations
-- Population: WorkOrder; expected: WO-2024-000001, WO-2025-005504 and WO-2026-010075, all Closed
SELECT wo.WorkOrderID, wo.WorkOrderNumber, wo.Status,
    wo.ReleasedDate, wo.ClosedDate
FROM WorkOrder AS wo
    LEFT JOIN WorkOrderOperation AS op
        ON op.WorkOrderID = wo.WorkOrderID
WHERE op.WorkOrderOperationID IS NULL
ORDER BY wo.WorkOrderNumber;
```

**Step 6. Look at the time recorded on them.** A hint, beyond the exercise: the model script sums the labor time of the work orders found in Step 5, with the Step 5 left join as a subquery in `WHERE lt.WorkOrderID IN (...)`.

**Check:** three work orders, WO-2024-000001, WO-2025-005504, WO-2026-010075, all Closed, so closed work orders exist without operations. Step 6 shows 18 direct entries and 45.86 hours recorded on them, nearly all with an operation key that matches nothing, which Step 7 isolates.

### Requirement (5): Operation keys that match nothing

**Step 7. Find the entries whose operation key points nowhere.**

```sql
-- Requirement (5): labor time whose WorkOrderOperationID matches no operation
-- Population: LaborTimeEntry with a WorkOrderOperationID; expected: 17 entries, 42.12 hours
SELECT lt.LaborTimeEntryID, lt.LaborType, lt.EmployeeID,
    wo.WorkOrderNumber, lt.WorkOrderOperationID, lt.WorkDate,
    lt.RegularHours + lt.OvertimeHours AS Hours
FROM LaborTimeEntry AS lt
    LEFT JOIN WorkOrderOperation AS op
        ON op.WorkOrderOperationID = lt.WorkOrderOperationID
    LEFT JOIN WorkOrder AS wo ON wo.WorkOrderID = lt.WorkOrderID
WHERE lt.WorkOrderOperationID IS NOT NULL
    AND op.WorkOrderOperationID IS NULL
ORDER BY wo.WorkOrderNumber, lt.WorkDate;
```

**Step 8. Group them by work order.**

```sql
-- Requirement (5): the same entries by work order
-- Population: as above; expected: WO-2024-000001 4, WO-2025-005504 6, WO-2026-010075 7
SELECT wo.WorkOrderNumber, COUNT(*) AS Entries,
    ROUND(SUM(lt.RegularHours + lt.OvertimeHours), 2) AS Hours
FROM LaborTimeEntry AS lt
    LEFT JOIN WorkOrderOperation AS op
        ON op.WorkOrderOperationID = lt.WorkOrderOperationID
    LEFT JOIN WorkOrder AS wo ON wo.WorkOrderID = lt.WorkOrderID
WHERE lt.WorkOrderOperationID IS NOT NULL
    AND op.WorkOrderOperationID IS NULL
GROUP BY wo.WorkOrderID, wo.WorkOrderNumber
ORDER BY wo.WorkOrderNumber;
```

**Check:** 17 entries and 42.12 hours, all direct: WO-2024-000001 4, WO-2025-005504 6, WO-2026-010075 7. They are the entries of the work orders of Step 5, apart from one entry that has no key at all. **Watch for:** without the IS NOT NULL test the anti-join returns 17,762 rows, the 17 orphans plus 17,745 entries that have no key, among them all the indirect and non-manufacturing time. A test on the entry's own key, `WorkOrderOperationID IS NULL`, finds those 17,745 and none of the 17.

### Requirement (6): The findings

**Step 9. Classify each finding.** See "What a strong answer says".

Indirect time ends a week earlier (2026-12-04): the records after it hold only direct and non-manufacturing time. (2) six GLEntry rows with SourceDocumentType PayrollPayment point to no payment: GLEntryIDs 7231 and 7232 (2024-01-19, SourceDocumentID 1), 12521 and 12522 (2025-01-03, SourceDocumentID 2646), 18069 and 18070 (2026-01-02, SourceDocumentID 5420), each pair a 7,971.10 debit "Clear accrued payroll" and a 7,971.10 credit "Disburse payroll cash"; debits and credits 23,913.30 each. They are ledger postings without a supporting document (planted missing payroll payment), an integrity failure to investigate. (3) Nine customers have no orders in the extract, all with IsActive 0, consistent with dormant accounts; their setup and deactivation records are the evidence that confirms it. (4) Three work orders have no operations, WO-2024-000001, WO-2025-005504, and WO-2026-010075, all Closed (planted), a process exception: a closed work order should have operations. Their RoutingIDs resolve, so what is missing is the work order operation records, not a routing. They do have labor: 18 direct time entries. (5) 17 Direct Manufacturing entries (42.1 hours) carry a WorkOrderOperationID that matches no operation: 4 on WO-2024-000001, 6 on WO-2025-005504, and 7 on WO-2026-010075, the work orders of requirement (4). An orphaned key, not a missing one, so an IS NULL filter alone would miss them; an integrity failure to correct. (Three more direct entries have no WorkOrderOperationID at all, Exercise 9.6.)

## What a strong answer says

- **Requirement (1).** Indirect and non-manufacturing time has no operation by design; manufacturing time starts in the first month of the window. The three direct entries with no operation and the end on December 11, 2026 are not expected, and the second is a timeliness limit on any test of the year's labor.
- **Requirement (6).** Four findings, each with a class and a follow-up.
  1. The six ledger rows with no payment are an integrity failure: postings without a supporting document. Ask payroll for the payment records and the bank evidence, and whether cash was disbursed.
  2. The nine customers with no orders are an expected condition on this evidence, dormant accounts. Check their setup and deactivation records.
  3. The three work orders without operations are a process exception: a closed work order should have work order operations, and their routing references resolve. Ask production why no operation records were kept for them and what the time recorded on them was for.
  4. The 17 entries with an orphaned key are an integrity failure. Correct the keys, and ask how the time system accepted an operation that does not exist.

A weak table calls every finding an integrity failure, or recommends no follow-up for the expected condition, or treats an empty result as a clean one without saying which direction was tested.

## Common mistakes and how to respond

- **No document type in the ledger test.** *Symptom:* 474,622 rows. *Response:* ask which rows should be tested at all.
- **NOT IN taken as always safe.** *Symptom:* a rule written from this result. *Response:* ask whether the list can hold a NULL.
- **A filter on IsActive.** *Symptom:* 0 rows. *Response:* ask what the test was meant to find.
- **A test on the entry's key only.** *Symptom:* 17,745 rows and none of the 17. *Response:* ask what a filled-in key that matches nothing looks like.
- **No IS NOT NULL test.** *Symptom:* 17,762 rows. *Response:* ask which of them are errors and which are expected.
- **Everything is a failure.** *Symptom:* a table with one class. *Response:* ask which findings the design explains.
