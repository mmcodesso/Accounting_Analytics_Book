# Exercise 11.6: Requisitions Just Under the Approval Threshold

{{ header() }}

## Purpose and learning outcomes

Exercise 8.5 counted purchase requisitions just below $5,000, the lowest nonzero approval limit in the Employee table. The audit senior asks for the test again with window functions, which can also find requisitions that look split: several consecutive requisitions for the same amount. The exercise combines a banded count, an outer join that must keep the unapproved rows, and LAG and LEAD with a join back to list a whole run. The analytics type is diagnostic, with a memo that proposes procedures and does not conclude.

By the end, students can:

- count rows in bands with an integer expression and a half-open interval (outcome 1);
- list the requisitions in a band with their requester and approver, keeping those with no approver (outcome 1);
- find equal neighbors with LAG and LEAD, and list every row of each run by joining back (outcome 3);
- write a memo that treats counts as a screen and names the next procedures.

**Competencies practiced.** CPA Evolution Core S2 M5 (risk of fraud and noncompliance) and ISC M2 (tests of internal controls); IMA Reporting and Control (internal control); IFAC IES 2 (f) and (g); AACSB A5 part 5.1.

## Step-by-step solution

### Requirement (1): The bands

**Step 1. Count the requisitions in each $50 band.**

```sql
-- Requirement (1): requisitions in $50 bands from $4,700 to $5,250
-- Population: all purchase requisitions; expected: the band just below $5,000 the largest
WITH Amounts AS (
    SELECT RequisitionID, RequisitionNumber, RequestDate,
        RequestedByEmployeeID, ApprovedByEmployeeID, Status,
        ROUND(Quantity * EstimatedUnitCost, 2) AS Amount
    FROM PurchaseRequisition
)
SELECT 4700 + 50 * CAST((Amount - 4700) / 50 AS INTEGER) AS BandFrom,
    COUNT(*) AS Requisitions
FROM Amounts
WHERE Amount >= 4700 AND Amount < 5250
GROUP BY BandFrom
ORDER BY BandFrom;
```

**Check:** 11 rows with {{ bands|join(', ') }}. The band from $4,950 holds {{ bands[5] }} against {{ bands[4] }} just below it and {{ bands[6] }} just above, at least twice either neighbor. **Watch for:** without the `CAST ... AS INTEGER` the division is real, and each distinct amount lands in a band of its own: {{ g.nocast }} rows for the {{ g.n_in_range }} requisitions in the range.

### Requirement (2): The band's requisitions

**Step 2. List the requisitions from $4,950.00 to $4,999.99 with requester and approver.**

```sql
-- Requirement (2): the requisitions from $4,950.00 to $4,999.99
-- Population: all purchase requisitions; expected: 18 requisitions
WITH Amounts AS (
    SELECT RequisitionID, RequisitionNumber, RequestDate,
        RequestedByEmployeeID, ApprovedByEmployeeID, Status,
        ROUND(Quantity * EstimatedUnitCost, 2) AS Amount
    FROM PurchaseRequisition
)
SELECT a.RequisitionNumber, a.Amount, a.RequestDate, a.Status,
    a.RequestedByEmployeeID, rq.JobTitle AS RequestedBy,
    a.ApprovedByEmployeeID, ap.JobTitle AS ApprovedBy
FROM Amounts AS a
    INNER JOIN Employee AS rq ON rq.EmployeeID = a.RequestedByEmployeeID
    LEFT JOIN Employee AS ap ON ap.EmployeeID = a.ApprovedByEmployeeID
WHERE a.Amount BETWEEN 4950 AND 4999.99
ORDER BY a.Amount DESC, a.RequisitionNumber;
```

**Check:** {{ g.band }} rows, {{ g.no_approver }} of them with no approver. **Watch for:** an INNER JOIN to the approver returns {{ g.inner }} rows and drops the {{ g.no_approver }} requisitions with no approver, the ones the audit senior most wants to see; the join to the approver must be a LEFT JOIN. The requester can be an inner join, because every requisition has one.

### Requirement (3): The runs of equal amounts

**Step 3. Find the middle row of each run, and list every row of it.**

```sql
-- Requirement (3): each run of three consecutive requisitions for the same amount
-- Population: requisitions in RequisitionID order; expected: the rows of each run
WITH Amounts AS (
    SELECT RequisitionID, RequisitionNumber, RequestDate,
        RequestedByEmployeeID, ApprovedByEmployeeID, Status,
        ROUND(Quantity * EstimatedUnitCost, 2) AS Amount
    FROM PurchaseRequisition
),
Neighbors AS (
    SELECT RequisitionID, Amount,
        LAG(Amount) OVER (ORDER BY RequisitionID) AS PreviousAmount,
        LEAD(Amount) OVER (ORDER BY RequisitionID) AS NextAmount,
        LAG(RequisitionID) OVER (ORDER BY RequisitionID) AS PreviousID,
        LEAD(RequisitionID) OVER (ORDER BY RequisitionID) AS NextID
    FROM Amounts
),
Runs AS (
    SELECT RequisitionID AS MiddleID, PreviousID, NextID
    FROM Neighbors
    WHERE Amount = PreviousAmount AND Amount = NextAmount
)
SELECT r.MiddleID, a.RequisitionID, a.RequisitionNumber, a.RequestDate,
    a.Amount, a.RequestedByEmployeeID, a.ApprovedByEmployeeID, a.Status
FROM Runs AS r
    INNER JOIN Amounts AS a
        ON a.RequisitionID BETWEEN r.PreviousID AND r.NextID
ORDER BY a.RequisitionID;
```

**Check:** {{ g.joined }} rows, {{ runs|length }} runs of three at ${{ amount|money }}, each on 1 January of its year. **Watch for:** requiring both neighbors to match flags only the middle row of each run, {{ middles|join(' and ') }}, because the first and last rows each have one neighbor that differs. The join back with `BETWEEN r.PreviousID AND r.NextID` lists all three. Testing only the previous neighbor flags {{ g.prev_only }} rows, more than the runs account for, because a pair of equal amounts that is not a run also qualifies.

### Requirement (4): The people in each run

**Step 4. Report the requesters and approvers of each run, and whether any requisition has no approver.** The model script groups the Runs CTE by MiddleID and reports the first and last requisition number, the first date, `GROUP_CONCAT` of the requesters and of the approvers' job titles, and `SUM(CASE WHEN ApprovedByEmployeeID IS NULL THEN 1 ELSE 0 END)`.

**Check:** two rows: {% for r in runs %}the run from {{ r.first }} to {{ r.last }} with requesters {{ r.requesters|join(', ') }}{{ "; " if not loop.last else "." }}{% endfor %} Each run has two requisitions with no approver and one approved by employee {{ cfo }}, the chief financial officer. **Watch for:** `ApprovedByEmployeeID = NULL` counts {{ g.eq_null }} where `IS NULL` counts {{ g.is_null }} across the two runs, and a run's approver list shows one title, not three, because GROUP_CONCAT skips NULLs.

## What a strong answer says

- **The counts are a screen.** The band just below the limit holds {{ bands[5] }}, against {{ bands[4] }} and {{ bands[6] }} on either side, which is unusual but not evidence of splitting by itself.
- **The runs are the stronger evidence.** Two runs of three equal amounts, each on 1 January of its year, with two requisitions in each run unapproved and the third approved by the chief financial officer, all converted to purchase orders.
- **Two readings.** The pattern is consistent with a purchase split to stay under the limit and with requisitions that bypassed approval. The six unapproved requisitions of Exercise 2.5 are among the rows, and all of them sit just below the limit.
- **Next procedures.** Obtain the purchase orders and supplier invoices behind the runs and test whether each run is one need; ask the requesters and the purchasing manager why the requisitions were raised separately and how they were converted without approval; test the system control that should block converting an unapproved requisition; extend the band test to the other limits and to the same item and requester within a few days.

A weak memo says that the plant splits purchases, or reports the band count with no runs and no next step.

## Common mistakes and how to respond

- **No CAST in the band.** *Symptom:* {{ g.nocast }} rows. *Response:* ask what dividing two real numbers returns.
- **An INNER JOIN to the approver.** *Symptom:* {{ g.inner }} rows. *Response:* ask which requisitions have no approver.
- **Only the middle rows listed.** *Symptom:* {{ middles|length }} rows for two runs. *Response:* ask which rows belong to a run.
- **`= NULL`.** *Symptom:* {{ g.eq_null }} without an approver. *Response:* ask what a comparison with NULL returns.
- **A conclusion in the memo.** *Symptom:* "the requisitions were split". *Response:* ask what evidence separates a split from a bypass.
