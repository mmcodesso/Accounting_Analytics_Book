## Purpose and learning outcomes

Tutorial 8.2 aged the receivables in Excel, and Tutorial 12.2 reconciled the goods received but not invoiced to account `2020` in total. The controller now wants both balances at the end of fiscal {{ g.y }} in SQL, so that they can be aged and reconciled at every year-end without a workbook. The audit mindset: a population is reconciled to the ledger before anything is built on it, an unexplained difference is the first finding, and how a balance is built decides what the test can see. The analytics type is descriptive for the aging and diagnostic for the reconciliations.

Students can:

- build an open balance from pre-summed receipts and credits, with the as-of date in a one-row CTE (Requirement 1);
- age it with CASE and julianday, reconcile it to account `1020` and explain the difference and the credit balances (Requirement 2);
- stratify customers by key and pick the key items (Requirement 3);
- reconcile receipts not yet invoiced to account `2020` and date the oldest (Requirement 4);
- report the two balances in a memo (Requirement 5).

## Step-by-step solution

### Requirement (1): The open balance of each invoice

**Step 1. Subtract what was applied and credited.** Params holds the as-of date, Applied and Credited sum the receipts and credit memos of each invoice to that date, and Balances joins both to SalesInvoice and keeps the invoices dated by the as-of date. Every later test reuses these four CTEs.

```sql
-- Exercise 12.2, test A1: the open balance of each sales invoice at the as-of date
-- Population: invoices dated by 2026-12-31; expected: the open receivables
WITH Params AS (
    SELECT '2026-12-31' AS AsOfDate
),
Applied AS (
    SELECT SalesInvoiceID, SUM(AppliedAmount) AS Applied
    FROM CashReceiptApplication
    WHERE ApplicationDate <= (SELECT AsOfDate FROM Params)
    GROUP BY SalesInvoiceID
),
Credited AS (
    SELECT OriginalSalesInvoiceID AS SalesInvoiceID,
        SUM(GrandTotal) AS Credited
    FROM CreditMemo
    WHERE CreditMemoDate <= (SELECT AsOfDate FROM Params)
    GROUP BY OriginalSalesInvoiceID
),
Balances AS (
    SELECT si.SalesInvoiceID, si.InvoiceNumber, si.CustomerID,
        si.InvoiceDate, si.DueDate, si.GrandTotal,
        COALESCE(a.Applied, 0) AS Applied,
        COALESCE(c.Credited, 0) AS Credited,
        ROUND(si.GrandTotal - COALESCE(a.Applied, 0)
            - COALESCE(c.Credited, 0), 2) AS OpenBalance,
        julianday((SELECT AsOfDate FROM Params))
            - julianday(si.DueDate) AS DaysPastDue
    FROM SalesInvoice AS si
        LEFT JOIN Applied AS a ON a.SalesInvoiceID = si.SalesInvoiceID
        LEFT JOIN Credited AS c ON c.SalesInvoiceID = si.SalesInvoiceID
    WHERE si.InvoiceDate <= (SELECT AsOfDate FROM Params)
)
SELECT InvoiceNumber, CustomerID, InvoiceDate, DueDate, GrandTotal,
    ROUND(Applied, 2) AS Applied, ROUND(Credited, 2) AS Credited,
    OpenBalance
FROM Balances
WHERE OpenBalance > 0
ORDER BY CustomerID, InvoiceDate;
```

**Check:** {{ g.n_a1|count }} rows, ${{ g.a3[0]|money }} from {{ g.n_customers|count }} customers. **Watch for:** without COALESCE (`a.Applied` and `c.Credited` as they come) an invoice with no receipt or credit has a NULL balance, and the query returns {{ g.no_coalesce|count }} rows: a clean-looking result that has lost almost the whole population.

### Requirement (2): The aging and the reconciliation

**Step 2. Assign each balance to a bucket.** The four CTEs stay; the final query is a CASE on DaysPastDue, the as-of date less DueDate.

```sql
SELECT
    CASE
        WHEN DaysPastDue <= 0 THEN 'Current'
        WHEN DaysPastDue <= 30 THEN '1-30 days'
        WHEN DaysPastDue <= 60 THEN '31-60 days'
        WHEN DaysPastDue <= 90 THEN '61-90 days'
        ELSE 'Over 90 days'
    END AS AgingBucket,
    COUNT(*) AS Invoices, ROUND(SUM(OpenBalance), 2) AS OpenBalance
FROM Balances
WHERE OpenBalance > 0
GROUP BY AgingBucket
ORDER BY MIN(DaysPastDue);
```

### Requirement (3): Customers

**Step 4. Total by customer and stratify.** A Customers CTE groups the positive balances by CustomerID; the final query assigns a stratum with CASE and counts customers and share.

```sql
SELECT
    CASE
        WHEN OpenBalance < 1000 THEN 'Under 1,000'
        WHEN OpenBalance < 10000 THEN '1,000-9,999'
        WHEN OpenBalance < 50000 THEN '10,000-49,999'
        ELSE '50,000 and over'
    END AS Stratum,
    COUNT(*) AS Customers, ROUND(SUM(OpenBalance), 2) AS OpenBalance,
    ROUND(SUM(OpenBalance) / (SELECT SUM(OpenBalance) FROM Customers), 3)
        AS ShareOfBalance
FROM Customers
GROUP BY Stratum
ORDER BY MIN(OpenBalance);
```

## What a strong answer says

- **(2)** Almost everything past due is under a month late. The difference is the unsupported opening line, a finding to investigate and, if unsupported, to write off. The credit balances are liabilities to customers, not receivables.
- **(3)** The key items are the customers of $50,000 or more, chosen by key, not name.
- **(4)** The receipts agree with account `2020` except for rounding, which supports the liability but not its completeness: a receipt never recorded is missing from both. Old receipts need follow-up.
- **(5)** Each number comes with a disposition. A weak memo repeats the tables.

## Common mistakes and how to respond

- **A balance without COALESCE.** *Symptom:* {{ g.no_coalesce|count }} rows. *Response:* ask what a NULL does in subtraction.
- **Aging from the invoice date.** *Symptom:* {{ g.inv_over90 }} invoices over 90 days. *Response:* ask what "past due" is measured from.
- **Negative balances kept.** *Symptom:* an oldest bucket that is negative. *Response:* ask who owes whom.
- **Customers by name.** *Symptom:* {{ g.by_name }} customers. *Response:* ask what identifies a customer.
- **Receipts joined to invoice lines directly.** *Symptom:* {{ g.direct_rows|count }} lines. *Response:* ask how many invoice lines one receipt line has.
- **The difference called an error.** *Symptom:* a memo that asks for a correction. *Response:* ask what entry the amount equals.
