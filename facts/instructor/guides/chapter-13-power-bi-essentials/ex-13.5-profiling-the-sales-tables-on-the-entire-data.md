# Exercise 13.5: Profiling the Sales Tables on the Entire Data Set

{{ header() }}

## Purpose and learning outcomes

An auditor will not rely on a report whose data were profiled on a sample. The exercise repeats Tutorial 13.1's profile on four Tables and counts the difference: the first rows of the invoice tables are the earliest records, dated before any promotion and almost all paid, so they look cleaner and simpler than the Tables are. It also trains the judgment that follows a profile. A blank can be meaningful, a defect, or a follow-up, and a profile describes what is in the Tables without saying why. The analytics type is descriptive.

Students can:

- import Tables for profiling only, correcting the types that the first 200 rows get wrong, and keep them out of the model (Requirement 1);
- record empty and distinct values on the top rows and on the entire data set (Requirements 2 and 3);
- explain why the first rows are not representative (Requirement 3);
- classify blanks as meaningful, expected to exist or a follow-up (Requirement 4);
- document a profile in a memo with an attached table (Requirement 5).

**Competencies practiced.** CPA Evolution Core S1 M8 (extracting, transforming and cleansing financial data) and ISC M4 (use and management of data); IMA Data Analytics and Insights (data governance and data literacy); IFAC IES 2 (f) (audit) and IES 2 (i) (judging the adequacy of information technology processes and controls); AACSB A5 part 5.1.

### Requirement (4): Meaningful, expected or follow-up

**Step 4. Classify three columns.** The model classification:

- PromotionID: a meaningful blank, because most lines carry no promotion.
- PaymentDate: meaningful on the {{ unpaid_open|count }} open invoices, a follow-up on the {{ unpaid_settled }} Settled invoices that show no date.
- PriceListLineID and ShipmentLineID: empty on the same {{ base|count }} lines, the Base List lines, which are design services priced from the base list and shipping nothing.
- CollectionName: empty on {{ fur_word }} Furniture items, a follow-up, because {{ item }} was ordered under the {{ collection }} promotion.

**Check:** a reason that cites the column and the table, not "it looks normal". Accept other reasoned classifications. The other Item blanks depend on each item's type and supply mode, so read them by those before calling them errors.

## What a strong answer says

- **(2) and (3)** The four columns that change, with both figures, and the columns that do not. The explanation is the billing order, the dates and the promotions, not "a sample is small".
- **(4)** Each classification names the column, the table and the reason. A strong answer separates "blank by design" from "blank that should hold a date".
- **(5)** The memo says what the profile covers and what it cannot say: it describes the Tables, and does not show why an exception occurred.

## Common mistakes and how to respond

- **Discount left whole.** *Symptom:* {{ g.distinct_whole }} distinct value on both bases. *Response:* ask what the type icon shows and what a whole number does to a rate of `0.08`.
- **A conclusion from the top rows.** *Symptom:* "no line carries a promotion". *Response:* ask what the status bar says.
- **The wrong denominator.** *Symptom:* PromotionID's {{ g.top_rows|count }} empty values read against {{ n|count }} rows, {{ (g.top_rows / n)|pct }}. *Response:* ask which rows the share is of.
- **Every blank an error, or none.** *Symptom:* a list of blanks to fix, or "all fine". *Response:* ask which are blank by design.
- **Queries loaded.** *Symptom:* four extra tables in the model. *Response:* clear Enable load.
- **No attached table.** *Symptom:* figures only in prose. *Response:* ask where the auditor will look.

## Extensions and discussion questions

- Profile the Tables of a case chapter the same way and rank the columns by how far they move.
- Test the claim that the first rows predate the promotions, with a query in SQL or a table in the report.
- Discuss: should a report carry its own profile, and where?
- Discuss: which of these blanks would you ask the owner of the master data to fix?
