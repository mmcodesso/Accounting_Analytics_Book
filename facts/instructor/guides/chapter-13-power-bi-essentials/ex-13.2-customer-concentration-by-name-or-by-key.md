# Exercise 13.2: Customer Concentration by Name or by Key

{{ header() }}

## Purpose and learning outcomes

The controller wants to know whether any customer is a concentration that the audit committee should hear about. The answer is no, and the exercise earns its place by what happens on the way: a table grouped by CustomerName treats two different customers as one, and the Top N filter that selects the ten largest is invisible on the page. Chapter 3's rule that a name is not a key meets Chapter 13's rule that a filter the reader cannot see belongs in the title. The analytics type is descriptive.

Students can:

- rank customers with a Top N filter inside a table visual (Requirements 1 and 2);
- explain a difference between a list by name and a list by key (Requirement 2);
- find the names that belong to more than one CustomerID and state their revenue (Requirement 3);
- compute concentration shares and compare them with a policy (Requirement 4);
- state a hidden filter in a title (Requirement 5).

**Competencies practiced.** CPA Evolution Core S1 M8 (data mining and analysis of financial data) and ISC M4 (use and management of data); IMA Data Analytics and Insights (data literacy) and Reporting and Control (financial statement analysis); IFAC IES 2 (a) and IES 4 (a) (professional skepticism and judgment); AACSB A5 part 5.1.

## Step-by-step solution

### Requirement (1): The ranked list by name

**Step 1. Build the table and its Top N filter.**

a. Add a page named `Ex 13.2`, as in Exercise 13.1.
b. Select **Table**, and drag CustomerName from **Customer** and LineTotal from **SalesInvoiceLine** into **Columns**.
c. In the **Filters** pane, drag FiscalYear from **SalesInvoice** into **Filters on this page** and select {{ g.y }}.
d. Drag CustomerName into **Filters on this visual**, choose the filter type **Top N**, set it to the top 10 items by LineTotal, and apply it.
e. Sort the table by LineTotal, largest first, and give it the title `Top 10 customers by revenue, fiscal {{ g.y }} (grouped by name)`.

**Check:** ten rows. {{ merged.name }} is {{ merged.rank }} with ${{ merged.amount|money }}, and the total row reads ${{ g.sum_name|money }}. **Watch for:** the year missing from the filters. The amounts and the total row then cover every year, and the page no longer ties to the Validation page.

### Requirement (2): The ranked list by key

**Step 2. Rank by CustomerID.**

a. Add a second **Table** with CustomerID, CustomerName and LineTotal.
b. Click the arrow beside CustomerID in **Columns** and choose **Don't summarize**.
c. Drag CustomerID into **Filters on this visual**, choose **Top N**, set the top 10 items by LineTotal, and apply it. Sort and title the table as in Step 1, with `(grouped by CustomerID)`.

**Check:** the tenth customer is {{ tenth.name }} ({{ tenth.id }}), ${{ tenth.amount|money }}. Neither of {{ merged.name }}'s two customers is on the list: CustomerID {{ merged.parts[0].id }} ranks {{ merged.parts[0].rank }} and CustomerID {{ merged.parts[1].id }} ranks {{ merged.parts[1].rank }}. The lists differ by one customer: the name list holds {{ merged.name }} and the key list holds {{ tenth.name }}, which grouping by name pushes to {{ tenth.rank }}. The key is right, because a name is not an identity. The total row reads ${{ g.sum_key|money }}. **Watch for:** a lower total. If Top N ranked over a different set of years than the amounts show, the {{ g.y }} revenue of the ten best customers over all years adds to ${{ g.wrong_sum|money }}. Also CustomerID left at Sum. The table then groups by CustomerName alone, the list becomes the one by name, and {{ merged.name }} shows CustomerID {{ g.merged_id_sum }}, the sum of {{ g.merged_ids }}.

### Requirement (3): Names that carry two keys

**Step 3. Count the CustomerIDs behind each name.**

a. Add a **Table** with CustomerName and CustomerID from **Customer**, and set CustomerID to **Count (Distinct)**. Sort it from the largest count.
b. Add another **Table** with CustomerName, CustomerID, CustomerSegment and Region from **Customer** and LineTotal. Filter it to fiscal {{ g.y }}, and in **Filters on this visual** select the two names with a count of {{ g.shared[0][3] }}.

**Check:** the first table puts {{ g.shared[0][0] }} and {{ g.shared[1][0] }} on top with a count of {{ g.shared[0][3] }}, and every other name has one: {{ g.n_names }} names for {{ g.n_customers }} customers. The second shows {{ merged.name }} twice: CustomerID {{ merged.parts[0].id }} ({{ merged.parts[0].region }}, {{ merged.parts[0].segment }}) ${{ merged.parts[0].amount|money }} and CustomerID {{ merged.parts[1].id }} ({{ merged.parts[1].region }}, {{ merged.parts[1].segment }}) ${{ merged.parts[1].amount|money }}. {{ single.name }} appears once, CustomerID {{ single.id }}, ${{ single.amount|money }}. **Watch for:** reading {{ single.name }} as a second merged name. Only one of its two customers had fiscal {{ g.y }} revenue, so its by-name figure is the same as its by-key figure.

### Requirement (4): The shares

**Step 4. Divide.** A share is a ratio of totals, which a visual cannot give before Chapter 14's measures, so read the numbers and divide.

a. Read the largest customer's row in the by-key table and its total row.
b. Read fiscal {{ g.y }} revenue, ${{ g.revenue|money }}, from the Validation page.
c. Divide, and compare with the policy's threshold of ${{ g.threshold|money }}.

**Check:** the largest customer, {{ largest.name }} ({{ largest.id }}), holds {{ largest.share|pct }} of revenue and the second, {{ second.name }}, {{ second.share|pct }}. The ten largest by key hold {{ top_key|pct }}, and by name {{ top_name|pct }}. No customer reaches the policy, and the largest is under half of it. **Watch for:** dividing by the all-years total, ${{ g.all_rev|money }}, which makes the largest customer {{ g.largest_all|pct(2) }} and understates every share.

### Requirement (5): The title

**Step 5. State the filter.** Under **Format visual > General > Title**, make each title name the ranking and the period, `Top 10 customers by revenue, fiscal {{ g.y }}`, plus the grouping.

**Check:** a reader of the published page can tell that the table is a top ten and which year it covers. In **DAX query view**, the Checks tab's row for the name's rank runs this expression:


## What a strong answer says

- **(2)** The two lists differ by one customer. Grouping by name merged two customers, so the list overstates one name and pushes a real customer out of the ten. A strong answer ranks by key and shows the name beside it.
- **(3)** {{ merged.name }} is two customers, {{ merged.parts[0].id }} and {{ merged.parts[1].id }}, with their revenue; {{ single.name }} is two customers of which one sold.
- **(4)** The shares, the threshold and the conclusion that nothing reaches it. A strong answer notes that the by-name share is slightly higher only because of the merge.
- **(5)** A title that states the top ten, the measure and the year.

## Common mistakes and how to respond

- **Summed CustomerID.** *Symptom:* a CustomerID of {{ g.merged_id_sum }} on one row. *Response:* ask what a sum of identifiers means.
- **Ranking by name and calling it customers.** *Symptom:* {{ merged.name }} reported as one customer at ${{ merged.amount|money }}. *Response:* ask which CustomerIDs sit behind the name.
- **No year.** *Symptom:* amounts that match no fiscal {{ g.y }} figure. *Response:* ask which filter holds the year.
- **A share against the wrong total.** *Symptom:* a largest customer at {{ g.largest_all|pct(2) }}. *Response:* ask which revenue the policy refers to.
- **An unstated Top N.** *Symptom:* a title that says only `Customers`. *Response:* ask what the reader would think the table lists.
