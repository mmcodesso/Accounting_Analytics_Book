# Exercise 14.5: Testing the Model's Relationships

{{ header() }}

## Purpose and learning outcomes

Before the report is shared, the internal auditor reviews the model the way Chapter 12 reviewed queries: by testing what each relationship does to the numbers. The auditor does not change the model. The queries change a relationship for one calculation with CROSSFILTER, so the effect of Both is visible without being left in. The exercise makes the chapter's Watch out concrete: a two-way filter on a model with two fact tables carries a selection from one into the other. The analytics type is diagnostic.

Students can:

- count one thing three ways and say which count a report should use (Requirement 1);
- show a two-way filter leaking from sales into the ledger (Requirement 2);
- compare a share built with REMOVEFILTERS with one built with ALL on the fact table (Requirement 3);
- write a review list of settings with the test that reveals each (Requirement 4).

**Competencies practiced.** CPA Evolution Core S2 M4 (information technology and IT controls) and BAR M10 (advanced data analytics: data models and joins, dashboards); IMA Data Analytics and Insights (data governance) and Reporting and Control (internal control); IFAC IES 2 (i) (judging the adequacy of information and communications technology processes and controls) and IES 4 (a) (professional skepticism and professional judgment); AACSB A5 part 5.1.

## Before you assign

- **Files.** The copy after Tutorial 14.3 with both stars, and a DAX query view tab named `Ex 14.5` (the book says to double-click the tab to rename it). The model answer is the tab Ex 14.5; the Checks tab holds each value.
- **Data conditions.** Every invoice has its customer in the Customer table, so the three counts agree. The Customer table holds customers that did not buy in the year. Services invoices fall on only a few days of the year, which makes the leak visible. The ledger has postings every day of the year.
- **Verify first.** Every relationship of the copy is set to **Single**. The exercise changes none: a student who has changed one should undo it before running the queries.

## Step-by-step solution

### Requirement (1): Three counts of customers

**Step 1. Run the printed query.**

a. In **DAX query view**, open a new query tab and rename it `Ex 14.5`.
b. Type or paste the query from the exercise, select it and choose **Run**.

```dax jinja
{{ g.q1 }}
```

**Check:** one row for each item group, with a year filter of {{ g.y }} from TREATAS.

| Item group | Customer Rows | Customers Invoiced | Customer Rows Both |
|---|---:|---:|---:|
{% for x in invoiced %}
| {{ x.group }} | {{ customers|count }} | {{ x.n|count }} | {{ x.n|count }} |
{% endfor %}

Customer Rows is the Customer table, which a selection on Item or Date never reaches, because the filter flows from Customer to the lines and not back. Customers Invoiced is the distinct count on the fact table, the one a report should use. Customer Rows Both equals it: with Both, the lines filter Customer. The report uses the distinct count because Both gives the same answer here and changes every other measure that uses the relationship. **Watch for:** adding the groups. They sum to {{ g.sum_groups|count }}, against {{ n_invoiced|count }} customers in the year, because customers buy from several groups.

|---|---:|---:|
{% for x in others %}
| {{ x.group }} | ${{ x.opex|money }} | {{ x.days }} |
{% endfor %}
| {{ services.group }} | ${{ services.opex|money }} | {{ services.days }} |
| All groups | ${{ opex|money }} | {{ year_days }} |

The Services figure is the operating expense of the {{ services_word }} days on which design services were invoiced, a number with no meaning: a selection in the sales star has filtered the ledger through the shared Date table, as the Watch out on two fact tables warns. **Watch for:** a query with no year. Operating Expense then reads ${{ g.opex_all|money }}, the {{ years }} years, in every row, and the comparison stops being a test of the setting.

### Requirement (3): Two shares

**Step 3. Write the third query.** It shows each group's share with `REMOVEFILTERS ( 'Item' )` (the measure Share of Revenue) and with `ALL ( SalesInvoiceLine )`, and a row for the total.

```dax jinja
{{ g.q3 }}
```

**Check:**

| Item group | REMOVEFILTERS | ALL ( SalesInvoiceLine ) |
|---|---:|---:|
{% for s in shares %}
| {{ s.group }} | {{ s.rf|pct(2) }} | {{ s.all|pct(2) }} |
{% endfor %}
| All groups | {{ shares|sum(attribute='rf')|pct(2) }} | {{ all_total|pct(2) }} |

The first column adds to a whole and is each group's share of the year. The second adds to {{ all_total|pct(2) }}, the share of fiscal {{ g.y }} in the ${{ every|money }} of {{ years }} years, because ALL on the fact table removes the year as well. **Watch for:** a student who reads the total as a data error. The function is not at fault; the table it clears is.

### Requirement (4): The review list

**Step 4. Write the list.** Each item has its test:

| Look for | Test that reveals it |
|---|---|
| A relationship set to Both | Compare a count with and without CROSSFILTER (Step 1) |
| A count taken from a dimension or header table | Compare it with the distinct count on the fact table |
| ALL on a fact table inside a share | The shares must total a whole (Step 3) |
| An inactive relationship used without USERELATIONSHIP | A measure that equals its active twin (Exercise 14.2) |
| (Blank) members | Count the keys that find no match |
| Measures that keep the closing entries | The control totals of Exercise 14.6 |

## What a strong answer says

- **(1)** The three counts, why the first is constant, and the choice of the distinct count on the facts.
- **(2)** The Services row as the proof: the ledger's figure follows the sales selection, so the setting changes what other measures mean.
- **(3)** What each total is a share of, and that the fact table's ALL removes the year.
- **(4)** Each setting with a test, in the memo's own words, and the point that a test must be repeatable.

A strong answer gives a test for each item. A weak one lists settings to avoid.

## Common mistakes and how to respond

- **Both as harmless.** *Symptom:* "Customer Rows Both equals Customers Invoiced, so it is fine". *Response:* ask what Requirement 2 showed for the ledger.
- **Customer Rows as customers served.** *Symptom:* {{ customers|count }} in every group. *Response:* ask which customers bought in {{ g.y }}.
- **The groups added.** *Symptom:* {{ g.sum_groups|count }} customers. *Response:* ask whether a customer can buy in two groups.
- **No year in the query.** *Symptom:* Operating Expense of ${{ g.opex_all|money }}. *Response:* ask which filter fixes the year.
- **The total of the ALL column read as an error.** *Symptom:* a data complaint. *Response:* ask what the denominator holds.
- **A review list of preferences.** *Symptom:* "avoid Both". *Response:* ask what test would show it.
