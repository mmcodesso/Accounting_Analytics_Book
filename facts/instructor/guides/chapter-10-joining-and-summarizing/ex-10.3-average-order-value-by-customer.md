# Exercise 10.3: Average Order Value by Customer

{{ header() }}

## Purpose and learning outcomes

The sales manager wants to know which customers place the largest orders and whether order size differs by segment. The exercise is the chapter's first plain GROUP BY: a join, three aggregates, HAVING and a sort. Its lesson is the Watch out of the chapter: group by the key, not the name. The analytics type is descriptive, with a diagnostic habit: compare the row counts of two groupings and explain the difference.

By the end, students can:

- join SalesOrder to Customer and summarize by customer with COUNT, SUM and AVG (outcomes 1 and 3);
- show that a grouping by name merges two customers, by comparing row counts (outcome 3);
- filter groups with HAVING and rank them with ORDER BY and LIMIT (outcome 3);
- say what an average by segment tells a sales manager.

**Competencies practiced.** CPA Evolution BAR M10 (data models and joins) and Core S1 M8 (data mining and analysis of financial data); IMA Data Analytics and Insights (data analysis, data tools and techniques); IFAC IES 2 (b) and (i); AACSB A5 part 5.1.

## Before you assign

- **Files and software.** CharlesRiver_Work.sqlite and a script `Ex 10.3.sql`. Students need Tutorial 10.1 (joins, GROUP BY, HAVING).
- **Data conditions.** SalesOrder.OrderTotal is the order's total, so it must be summed over the orders and never over a join to the order lines. ## Step-by-step solution

### Requirement (1): Orders and average value by customer

**Step 1. Group the orders by customer key.**

```sql
-- Requirement (1): orders and average order value by customer
-- Population: SalesOrder, every order; expected: 211 customers, Glenn-Estrada first
SELECT c.CustomerID, c.CustomerName, c.CustomerSegment,
    COUNT(*) AS Orders,
    ROUND(SUM(so.OrderTotal), 2) AS TotalOrdered,
    ROUND(AVG(so.OrderTotal), 2) AS AverageOrder
FROM SalesOrder AS so
    INNER JOIN Customer AS c ON c.CustomerID = so.CustomerID
GROUP BY c.CustomerID, c.CustomerName, c.CustomerSegment
ORDER BY AverageOrder DESC;
```

**Step 2. Check the population.** Two short queries, the model answer's own, confirm the totals.

```sql
-- Requirement (1): all orders, the customers who placed them, and the average
-- Population: SalesOrder; expected: 5,819 orders, 211 customers, average 15,036.96
SELECT COUNT(*) AS Orders,
    COUNT(DISTINCT CustomerID) AS Customers,
    ROUND(AVG(OrderTotal), 2) AS AverageOrder
FROM SalesOrder;
```

```sql
-- Requirement (1): the customers in the master file
-- Population: Customer; expected: 220, so 9 have no orders
SELECT COUNT(*) AS Customers
FROM Customer;
```

**Check:** {{ customers }} rows, led by {% for t in top %}{{ t.name }} ({{ t.n }} orders, ${{ t.avg|money }}){{ ", " if not loop.last else "" }}{% endfor %}. The population is {{ orders|count }} orders from {{ customers }} of {{ g.n_customers }} customers, so {{ without }} have none, with an average of ${{ avg|money }}. **Watch for:** a LEFT JOIN from Customer with `COUNT(*)` returns {{ g.n_lj }} rows, and the {{ g.lj_one }} customers with no orders show one order and a NULL average. The average of the customers' averages is ${{ g.avg_of_avgs|money }}, not the order average. Joined to the order lines, `SUM(so.OrderTotal)` reads ${{ g.fan|money }} against ${{ g.true|money }}.

### Requirement (2): The same analysis by name

**Step 3. Group by CustomerName.**

```sql
-- Requirement (2): the same analysis grouped by CustomerName
-- Population: as (1); expected: 210 rows, one fewer than (1)
SELECT c.CustomerName, COUNT(*) AS Orders,
    ROUND(SUM(so.OrderTotal), 2) AS TotalOrdered,
    ROUND(AVG(so.OrderTotal), 2) AS AverageOrder
FROM SalesOrder AS so
    INNER JOIN Customer AS c ON c.CustomerID = so.CustomerID
GROUP BY c.CustomerName
ORDER BY AverageOrder DESC;
```

**Step 4. Find the names that cover more than one customer.**

```sql
-- Requirement (2): names that cover more than one customer with orders
-- Population: as (1); expected: Brown LLC, 2 customers
SELECT c.CustomerName,
    COUNT(DISTINCT c.CustomerID) AS Customers,
    COUNT(*) AS Orders
FROM SalesOrder AS so
    INNER JOIN Customer AS c ON c.CustomerID = so.CustomerID
GROUP BY c.CustomerName
HAVING COUNT(DISTINCT c.CustomerID) > 1;
```

**Check:** {{ g.n_by_name }} rows, one fewer than Step 1. {{ merged.name }} has {{ merged.customers|length }} customers: {% for c in merged.customers %}customer {{ c.id }} ({{ c.segment }}, {{ c.n }} orders, ${{ c.avg|money }}){{ ", " if not loop.last else "" }}{% endfor %}. By name they merge into one row of {{ g.merged_n }} orders averaging ${{ g.merged_avg|money }}, which describes neither; the merged row is number {{ g.name_rank }} in the ranking by name, while the two customers are numbers {{ g.id_ranks[0] }} and {{ g.id_ranks[1] }} in the ranking by key. **Watch for:** adding CustomerSegment to the grouping hides {{ g.hidden }}, because its customers sit in different segments, and leaves only {{ g.hidden_segment_pair }}. The model script also lists every shared name with its orders, a left join that shows that only customer {{ unmerged.ordering }} of {{ unmerged.name }} has orders.

### Requirement (3): Customers with at least 20 orders

**Step 5. Keep the groups with HAVING and take the ten highest averages.**

```sql
-- Requirement (3): the ten highest averages among customers with at least 20 orders
-- Population: as (1), HAVING 20 orders or more; expected: Glenn-Estrada first
SELECT c.CustomerID, c.CustomerName, c.CustomerSegment,
    COUNT(*) AS Orders,
    ROUND(AVG(so.OrderTotal), 2) AS AverageOrder
FROM SalesOrder AS so
    INNER JOIN Customer AS c ON c.CustomerID = so.CustomerID
GROUP BY c.CustomerID, c.CustomerName, c.CustomerSegment
HAVING COUNT(*) >= 20
ORDER BY AverageOrder DESC
LIMIT 10;
```

**Check:** 10 rows, led by {{ g.top_first }}; {{ g.n_min }} of the {{ customers }} customers have at least {{ g.min_orders }} orders. The ten are the same ten as without the HAVING, because every one of the ten has at least that many orders; the condition protects against a small sample and changes nothing here. **Watch for:** `WHERE COUNT(*) >= 20` stops with misuse of aggregate; a sort without DESC returns the ten lowest averages.

### Requirement (4): By segment

**Step 6. Group by CustomerSegment.**

```sql
-- Requirement (4): orders and average order value by segment
-- Population: as (1); expected: 5 segments, Strategic highest
SELECT c.CustomerSegment, COUNT(*) AS Orders,
    COUNT(DISTINCT c.CustomerID) AS Customers,
    ROUND(AVG(so.OrderTotal), 2) AS AverageOrder
FROM SalesOrder AS so
    INNER JOIN Customer AS c ON c.CustomerID = so.CustomerID
GROUP BY c.CustomerSegment
ORDER BY AverageOrder DESC;
```

**Check:** 5 rows, {% for s in segments %}{{ s[0] }} {{ s[1]|count }} orders at ${{ s[2]|money }}{{ "; " if not loop.last else "" }}{% endfor %}. The largest segment's average is {{ g.seg_ratio|num(1) }} times the smallest's.

## What a strong answer says

- **Requirement (5), the note.** Order size differs sharply by segment: the segment averages run from ${{ segments[-1][2]|money }} to ${{ segments[0][2]|money }}, a ratio of {{ g.seg_ratio|num(1) }}, so the mix of segments matters as much as the number of orders. The customers with the largest orders are {{ top[0].name }}, {{ top[1].name }} and {{ top[2].name }}.
- **Why the key.** The key identifies a customer and the name does not. Grouping by name returns {{ g.n_by_name }} rows instead of {{ customers }}, because two customers share {{ merged.name }}, and the merged row describes neither.

A weak note quotes the segment averages without a comparison, or answers the question about grouping with "the names are the same" and no row counts.

## Common mistakes and how to respond

- **Grouping by name.** *Symptom:* {{ g.n_by_name }} rows. *Response:* ask which customer the row belongs to.
- **A left join and `COUNT(*)`.** *Symptom:* {{ g.lj_one }} customers with one order and a NULL average. *Response:* ask what the average of nothing is.
- **OrderTotal summed over the order lines.** *Symptom:* a total of ${{ g.fan|money }}. *Response:* ask at what level OrderTotal is recorded.
- **An average of averages.** *Symptom:* an overall average of ${{ g.avg_of_avgs|money }}. *Response:* ask what weight each customer's average should carry.
- **COUNT in WHERE.** *Symptom:* misuse of aggregate. *Response:* ask whether the condition is about a row or a group.
- **A grouping that hides the duplicate.** *Symptom:* only {{ g.hidden_segment_pair }} found. *Response:* ask which columns decide whether two customers are the same.

## Extensions and discussion questions

- Compute the weighted average of the segment averages and show that it equals the order average, while the average of the customers' averages does not.
- Add the largest order of each customer with MAX, and say whether the average hides outliers.
- Discuss: should the sales manager care about the average order or the total ordered, and which segment needs which measure?
- Discuss: how would the controller learn that two records are the same customer, and what in the data would show it?
