# Exercise 10.5: Testing Referential Integrity with Anti-Joins

{{ header() }}

## Purpose and learning outcomes

Chapter 3 explained that the database declares no foreign keys, so its relationships must be tested. The audit senior wants a set of integrity tests run with anti-joins before the team relies on the joins in its other work. The exercise is the auditing counterpart of the chapter's left-join section: each requirement tests one parent-child pair, and the last asks the student to classify what was found. The analytics type is descriptive, with a diagnostic step in the classification.

By the end, students can:

- profile a table with the chapter's tests and say which results were expected (outcome 3);
- write an anti-join from a child to its parent with the right IS NULL test and the document type (outcome 2);
- find the parents that have no children, the other direction of the same test (outcome 2);
- separate a filled-in key that matches nothing from a missing key, and classify each finding as an integrity failure, a process exception or an expected condition.

**Competencies practiced.** CPA Evolution Core S2 M4 (information technology and IT controls) and BAR M10 (data models and joins); IMA Data Analytics and Insights (data governance) and Reporting and Control (internal control); IFAC IES 2 (i) and (f); AACSB A5 part 5.1.

## Before you assign

- **Files and software.** CharlesRiver_Work.sqlite and a script `Ex 10.5.sql`. Students need Tutorial 10.1 (LEFT JOIN, the anti-join) and Tutorial 10.3 (Steps 4 and 7), and Exercise 9.6, which found the direct entries with no operation, helps.
- **Data conditions.** The tests rely on conditions planted in the data: ledger rows of type PayrollPayment whose document does not exist, work orders without operations, and labor entries whose WorkOrderOperationID matches no operation. Customers without orders are all inactive. The profile shows time records ending before the year does.
- **Verify first.** `SELECT COUNT(*) FROM PayrollPayment;` returns {{ g.n_pay|count }} rows, and the ledger holds payroll postings for each of them.

## Step-by-step solution

### Requirement (1): The profile

**Step 1. Profile the labor time by labor type.**

```sql
-- Requirement (1): a profile of LaborTimeEntry by labor type
-- Population: LaborTimeEntry, every entry; expected: 3 labor types, 51,117 direct entries
SELECT LaborType, COUNT(*) AS Entries,
    COUNT(WorkOrderOperationID) AS WithOperation,
    COUNT(DISTINCT EmployeeID) AS Employees,
    MIN(WorkDate) AS FirstWorkDate,
    MAX(WorkDate) AS LastWorkDate
FROM LaborTimeEntry
GROUP BY LaborType
ORDER BY LaborType;
```

**Check:** direct {{ direct.n|count }} entries, {{ direct.ops|count }} with an operation, {{ direct.employees }} employees, {{ direct.first }} to {{ direct.last }}; indirect {{ indirect.n|count }}, {{ indirect.ops }} with an operation, {{ indirect.employees }} employees, {{ indirect.first }} to {{ indirect.last }}; non-manufacturing {{ nonmfg.n|count }}, {{ nonmfg.ops }}, {{ nonmfg.employees }}, {{ nonmfg.first }} to {{ nonmfg.last }}. Expected: indirect and non-manufacturing time has no operation by design, and manufacturing time starts in the first month of the window. Not expected: {{ no_op_word|lower }} direct entries with no operation (Exercise 9.6), and an end on {{ end_text }}, before the year ends. Indirect time ends {{ indirect_gap }} earlier. **Watch for:** WithOperation counts the filled operation keys, not valid links. The profile tests counts and coverage, not whether the keys resolve, and the anti-join of Step 7 finds {{ orphans }} filled keys that match no operation.

### Requirement (2): Ledger rows with no payroll payment

**Step 2. Find the ledger rows that point to no payment.**

```sql
-- Requirement (2): ledger rows that point to no payroll payment
-- Population: GLEntry, PayrollPayment; expected: six rows, three pairs of 7,971.10
SELECT gl.GLEntryID, gl.PostingDate, gl.SourceDocumentID,
    gl.Debit, gl.Credit, gl.Description
FROM GLEntry AS gl
    LEFT JOIN PayrollPayment AS pp
        ON pp.PayrollPaymentID = gl.SourceDocumentID
WHERE gl.SourceDocumentType = 'PayrollPayment'
    AND pp.PayrollPaymentID IS NULL
ORDER BY gl.GLEntryID;
```

**Step 3. Total the rows.**

```sql
-- Requirement (2): their totals
-- Population: as above; expected: debits and credits 23,913.30 each
SELECT COUNT(*) AS Postings,
    ROUND(SUM(gl.Debit), 2) AS Debits,
    ROUND(SUM(gl.Credit), 2) AS Credits
FROM GLEntry AS gl
    LEFT JOIN PayrollPayment AS pp
        ON pp.PayrollPaymentID = gl.SourceDocumentID
WHERE gl.SourceDocumentType = 'PayrollPayment'
    AND pp.PayrollPaymentID IS NULL;
```

**Check:** {{ n_orphans }} rows in {{ pairs|length }} pairs: {% for p in pairs %}{{ p.ids[0] }} and {{ p.ids[1] }} ({{ p.date }}, SourceDocumentID {{ p.doc }}){{ "; " if not loop.last else "" }}{% endfor %}. Each pair is a ${{ amount|money }} debit, "{{ debit_text }}", and credit, "{{ credit_text }}"; the totals are ${{ total|money }} each side. **Watch for:** without the document type the anti-join returns {{ g.no_type|count }} ledger rows whose numeric SourceDocumentID matches no PayrollPayment. They include the {{ n_orphans }} payroll orphans and many unrelated documents, while unrelated rows whose ID happens to equal a payment's drop out, so the count is not the non-payroll population either. NOT IN returns the same {{ g.not_in }} rows here, because the payment key is never NULL; that safety is a property of this column, not a rule. The test in the other direction, payments with no ledger rows, returns {{ g.reverse }} of {{ g.n_pay|count }}.

### Requirement (3): Customers with no orders

**Step 4. Find the customers that placed no order.**

```sql
-- Requirement (3): customers with no sales order in the database
-- Population: Customer; expected: nine customers, all inactive
SELECT c.CustomerID, c.CustomerName, c.CustomerSegment,
    c.IsActive
FROM Customer AS c
    LEFT JOIN SalesOrder AS so ON so.CustomerID = c.CustomerID
WHERE so.SalesOrderID IS NULL
ORDER BY c.CustomerID;
```

**Check:** {{ n_customers|lower }} customers, every one with IsActive 0, and they are all the inactive customers of the file. **Watch for:** adding `AND c.IsActive = 1` returns {{ g.active }} rows; the flag is something to read in the result, not a filter.

### Requirement (4): Work orders with no operations

**Step 5. Find the work orders that have no operations.**

```sql
-- Requirement (4): work orders with no work order operations
-- Population: WorkOrder; expected: WO-2024-000001, WO-2025-005504 and WO-2026-010075, all Closed
SELECT wo.WorkOrderID, wo.WorkOrderNumber, wo.Status,
    wo.ReleasedDate, wo.ClosedDate
FROM WorkOrder AS wo
    LEFT JOIN WorkOrderOperation AS op
        ON op.WorkOrderID = wo.WorkOrderID
WHERE op.WorkOrderOperationID IS NULL
ORDER BY wo.WorkOrderNumber;
```

**Step 6. Look at the time recorded on them.** A hint, beyond the exercise: the model script sums the labor time of the work orders found in Step 5, with the Step 5 left join as a subquery in `WHERE lt.WorkOrderID IN (...)`.

**Check:** {{ n_wo|lower }} work orders, {{ work_orders|join(', ') }}, all Closed, so closed work orders exist without operations. Step 6 shows {{ g.wo_labor_n }} direct entries and {{ g.wo_labor_hours|num(2) }} hours recorded on them, nearly all with an operation key that matches nothing, which Step 7 isolates.

### Requirement (5): Operation keys that match nothing

**Step 7. Find the entries whose operation key points nowhere.**

```sql
-- Requirement (5): labor time whose WorkOrderOperationID matches no operation
-- Population: LaborTimeEntry with a WorkOrderOperationID; expected: 17 entries, 42.12 hours
SELECT lt.LaborTimeEntryID, lt.LaborType, lt.EmployeeID,
    wo.WorkOrderNumber, lt.WorkOrderOperationID, lt.WorkDate,
    lt.RegularHours + lt.OvertimeHours AS Hours
FROM LaborTimeEntry AS lt
    LEFT JOIN WorkOrderOperation AS op
        ON op.WorkOrderOperationID = lt.WorkOrderOperationID
    LEFT JOIN WorkOrder AS wo ON wo.WorkOrderID = lt.WorkOrderID
WHERE lt.WorkOrderOperationID IS NOT NULL
    AND op.WorkOrderOperationID IS NULL
ORDER BY wo.WorkOrderNumber, lt.WorkDate;
```

**Step 8. Group them by work order.**

```sql
-- Requirement (5): the same entries by work order
-- Population: as above; expected: WO-2024-000001 4, WO-2025-005504 6, WO-2026-010075 7
SELECT wo.WorkOrderNumber, COUNT(*) AS Entries,
    ROUND(SUM(lt.RegularHours + lt.OvertimeHours), 2) AS Hours
FROM LaborTimeEntry AS lt
    LEFT JOIN WorkOrderOperation AS op
        ON op.WorkOrderOperationID = lt.WorkOrderOperationID
    LEFT JOIN WorkOrder AS wo ON wo.WorkOrderID = lt.WorkOrderID
WHERE lt.WorkOrderOperationID IS NOT NULL
    AND op.WorkOrderOperationID IS NULL
GROUP BY wo.WorkOrderID, wo.WorkOrderNumber
ORDER BY wo.WorkOrderNumber;
```

**Check:** {{ orphans }} entries and {{ orphan_hours|num(2) }} hours, all direct: {% for w in orphan_by_wo %}{{ w[0] }} {{ w[1] }}{{ ", " if not loop.last else "" }}{% endfor %}. They are the entries of the work orders of Step 5, apart from one entry that has no key at all. **Watch for:** without the IS NOT NULL test the anti-join returns {{ g.no_filter|count }} rows, the {{ g.orphans }} orphans plus {{ g.key_null|count }} entries that have no key, among them all the indirect and non-manufacturing time. A test on the entry's own key, `WorkOrderOperationID IS NULL`, finds those {{ g.key_null|count }} and none of the {{ g.orphans }}.

## What a strong answer says

- **Requirement (1).** Indirect and non-manufacturing time has no operation by design; manufacturing time starts in the first month of the window. The {{ no_op_word|lower }} direct entries with no operation and the end on {{ end_text }} are not expected, and the second is a timeliness limit on any test of the year's labor.
- **Requirement (6).** Four findings, each with a class and a follow-up.
  1. The {{ n_orphans }} ledger rows with no payment are an integrity failure: postings without a supporting document. Ask payroll for the payment records and the bank evidence, and whether cash was disbursed.
  2. The {{ n_customers|lower }} customers with no orders are an expected condition on this evidence, dormant accounts. Check their setup and deactivation records.
  3. The {{ n_wo|lower }} work orders without operations are a process exception: a closed work order should have work order operations, and their routing references resolve. Ask production why no operation records were kept for them and what the time recorded on them was for.
  4. The {{ orphans }} entries with an orphaned key are an integrity failure. They sit on the work orders that have no operations at all, so the operation records may be missing rather than the keys wrong. Establish which from the operation history and the source records, correct what that evidence supports through an authorized change that keeps the exception trail, and ask how the time system accepted an operation that does not exist.

A weak table calls every finding an integrity failure, or recommends no follow-up for the expected condition, or treats an empty result as a clean one without saying which direction was tested.

## Common mistakes and how to respond

- **No document type in the ledger test.** *Symptom:* {{ g.no_type|count }} rows. *Response:* ask which rows should be tested at all.
- **NOT IN taken as always safe.** *Symptom:* a rule written from this result. *Response:* ask whether the list can hold a NULL.
- **A filter on IsActive.** *Symptom:* {{ g.active }} rows. *Response:* ask what the test was meant to find.
- **A test on the entry's key only.** *Symptom:* {{ g.key_null|count }} rows and none of the {{ g.orphans }}. *Response:* ask what a filled-in key that matches nothing looks like.
- **No IS NOT NULL test.** *Symptom:* {{ g.no_filter|count }} rows. *Response:* ask which of them are errors and which are expected.
- **Everything is a failure.** *Symptom:* a table with one class. *Response:* ask which findings the design explains.

## Extensions and discussion questions

- Run the test in the other direction where it applies: payments with no ledger rows, operations with no work order. Which direction does each control need?
- Write the five tests as one script with a header and a comment above each query, the first step toward Chapter 12's library.
- Discuss: which of these findings would an enforced foreign key from child to parent prevent, and which need a NOT NULL rule, a process rule or a test that reads the source type? Why can a parent still have no children, and why can one ordinary foreign key not check a ledger reference whose table depends on SourceDocumentType?
- Discuss: the nine customers are an expected condition on this evidence. What evidence would change the class?
