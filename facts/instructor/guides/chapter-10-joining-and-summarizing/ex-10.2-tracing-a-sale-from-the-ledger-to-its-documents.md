# Exercise 10.2: Tracing a Sale from the Ledger to Its Documents

{{ header() }}

## Purpose and learning outcomes

Tutorial 3.2 traced {{ inv.number }} by filtering worksheets one at a time. The audit senior wants the trace done with joins, and then widened from one sale to every revenue posting of a year. The exercise practices a join from the ledger to a document through two columns, a join through SourceLineID to the line, and an anti-join as an existence test. The analytics type is diagnostic, and the memo adds the audit habit of saying what a test does not show.

By the end, students can:

- join ledger rows to their invoice with SourceDocumentType in the ON clause, and show that the postings balance (outcome 1);
- follow a revenue posting to its invoice line and item (outcomes 1 and 5);
- write an anti-join that tests a population, with its IS NOT NULL condition, and report the tested and the exceptions (outcome 2);
- state what an existence test shows and what it leaves open.

**Competencies practiced.** CPA Evolution BAR M10 (data models and joins) and Core S2 M9 (audit procedures and audit data analytics); IMA Data Analytics and Insights (data tools and techniques) and Reporting and Control (financial recordkeeping); IFAC IES 2 (a), (f) and (i); AACSB A5 part 5.1.

## Before you assign

- **Files and software.** CharlesRiver_Work.sqlite and a script `Ex 10.2.sql`. Students need Tutorial 10.1 (joins, LEFT JOIN, the anti-join) and Tutorial 3.2's trace.
- **Data conditions.** GLEntry.SourceDocumentType and SourceDocumentID name the document, and SourceLineID names its line for line-level postings only. The receivable, freight and tax postings of an invoice have no SourceLineID. Every SalesInvoice posting of the year that has a line points to an existing line of the invoice it names.
- **Verify first.** `SELECT COUNT(*) FROM GLEntry WHERE SourceDocumentID = {{ inv.id }};` returns {{ g.n_id_only|count }} rows, of which {{ g.n_correct }} belong to the invoice. That gap is the exercise's trap.

## How to run it

Individual, about 75 minutes: 10 for (1), 15 for (2), 25 for (3) and 25 for the memo. The routine for every step: type the two comment lines and the query at the end of the script, select them, click **Execute all/selected SQL** and read the message pane. ## Step-by-step solution

### Requirement (1): The ledger rows of the invoice

**Step 1. List the rows the invoice posted.**

```sql
-- Requirement (1): the ledger rows posted by SI-2025-007947
-- Population: GLEntry, SalesInvoice 7947; expected: four rows on 2025-03-05
SELECT gl.GLEntryID, gl.PostingDate, a.AccountNumber,
    a.AccountName, gl.Debit, gl.Credit, gl.SourceLineID,
    gl.Description
FROM GLEntry AS gl
    INNER JOIN SalesInvoice AS si
        ON gl.SourceDocumentType = 'SalesInvoice'
        AND si.SalesInvoiceID = gl.SourceDocumentID
    INNER JOIN Account AS a ON a.AccountID = gl.AccountID
WHERE si.InvoiceNumber = 'SI-2025-007947'
ORDER BY gl.GLEntryID;
```

{{ figure('IF-10-2-A') }}

**Step 2. Compare debits, credits and the invoice's total.**

```sql
-- Requirement (1): debits against credits and the invoice's total
-- Population: as above; expected: debits = credits = GrandTotal = 787.48
SELECT si.InvoiceNumber, si.SubTotal, si.FreightAmount,
    si.TaxAmount, si.GrandTotal,
    ROUND(SUM(gl.Debit), 2) AS Debits,
    ROUND(SUM(gl.Credit), 2) AS Credits
FROM GLEntry AS gl
    INNER JOIN SalesInvoice AS si
        ON gl.SourceDocumentType = 'SalesInvoice'
        AND si.SalesInvoiceID = gl.SourceDocumentID
WHERE si.InvoiceNumber = 'SI-2025-007947'
GROUP BY si.SalesInvoiceID, si.InvoiceNumber, si.SubTotal,
    si.FreightAmount, si.TaxAmount, si.GrandTotal;
```

**Step 3. Run the trap, for contrast.**

```sql
-- Requirement (1): the trap, ledger rows whose SourceDocumentID is 7947 in any document
-- Population: GLEntry; expected: 38 rows from 11 document types
SELECT COUNT(*) AS Postings,
    COUNT(DISTINCT SourceDocumentType) AS DocumentTypes
FROM GLEntry
WHERE SourceDocumentID = 7947;
```

**Check:** {{ n_rows }} rows on {{ posted }}: {% for r in rows %}{{ r.id }} {{ r.side }} ${{ r.amount|money }} to {{ r.number }} {{ r.name }}{{ "; " if not loop.last else "" }}{% endfor %}. Debits ${{ debits|money }}, credits ${{ credits|money }}, and the GrandTotal is the same: SubTotal ${{ inv.subtotal|money }}, freight ${{ inv.freight|money }}, tax ${{ inv.tax|money }}. The trap returns {{ trap_rows }} postings of {{ trap_types }} document types, so the ID alone is not a key. **Watch for:** Step 1 without the type condition returns {{ trap_rows }} rows, not {{ n_rows }}.

### Requirement (2): The customer, the line and the item

**Step 4. Join the invoice to its customer, lines and items.**

```sql
-- Requirement (2): SI-2025-007947 with its customer, lines and items
-- Population: SalesInvoice 7947; expected: customer 135, 1 line
SELECT si.InvoiceNumber, si.InvoiceDate, c.CustomerID,
    c.CustomerName, sil.SalesInvoiceLineID, i.ItemCode,
    i.ItemName, sil.Quantity, sil.UnitPrice, sil.LineTotal
FROM SalesInvoice AS si
    INNER JOIN Customer AS c ON c.CustomerID = si.CustomerID
    INNER JOIN SalesInvoiceLine AS sil
        ON sil.SalesInvoiceID = si.SalesInvoiceID
    INNER JOIN Item AS i ON i.ItemID = sil.ItemID
WHERE si.InvoiceNumber = 'SI-2025-007947';
```

**Step 5. Join the revenue posting to its line through SourceLineID.**

```sql
-- Requirement (2): the revenue posting joined to its invoice line through SourceLineID
-- Population: GLEntry, SalesInvoice 7947, rows with a SourceLineID; expected: GLEntry 126312 and line 10645
SELECT gl.GLEntryID, gl.SourceLineID, sil.SalesInvoiceLineID,
    i.ItemName, sil.LineTotal, gl.Credit
FROM GLEntry AS gl
    INNER JOIN SalesInvoiceLine AS sil
        ON sil.SalesInvoiceLineID = gl.SourceLineID
    INNER JOIN Item AS i ON i.ItemID = sil.ItemID
WHERE gl.SourceDocumentType = 'SalesInvoice'
    AND gl.SourceDocumentID = 7947;
```

**Check:** customer {{ inv.customer }} {{ inv.customer_name }}, one line. The revenue posting's SourceLineID is {{ line.id }}, the line of {{ line.name }}, {{ line.qty }} units at ${{ line.price|money }}, and the line's LineTotal equals the credit. **Watch for:** without the type condition the query returns {{ g.line_no_type }} rows, because the line IDs of other documents' tables also match an invoice line. Joined on the invoice ID instead of SourceLineID, it returns {{ g.line_by_invoice }} rows, one for each posting, so the receivable and tax rows look as if they posted the line.

### Requirement (3): The year's postings

**Step 6. Count the postings to test.**

```sql
-- Requirement (3): the fiscal 2026 SalesInvoice postings that carry a SourceLineID
-- Population: GLEntry, SalesInvoice, fiscal 2026; expected: 9,525 postings to test
SELECT COUNT(*) AS PostingsTested
FROM GLEntry
WHERE SourceDocumentType = 'SalesInvoice'
    AND FiscalYear = 2026
    AND SourceLineID IS NOT NULL;
```

**Step 7. Run the anti-join.**

```sql
-- Requirement (3): anti-join, postings whose SourceLineID matches no invoice line
-- Population: the 9,525 postings above; expected: no rows
SELECT gl.GLEntryID, gl.PostingDate, gl.VoucherNumber,
    gl.SourceLineID, gl.Credit
FROM GLEntry AS gl
    LEFT JOIN SalesInvoiceLine AS sil
        ON sil.SalesInvoiceLineID = gl.SourceLineID
WHERE gl.SourceDocumentType = 'SalesInvoice'
    AND gl.FiscalYear = 2026
    AND gl.SourceLineID IS NOT NULL
    AND sil.SalesInvoiceLineID IS NULL;
```

**Step 8. Add a test that the line belongs to the invoice named.** A hint, beyond the exercise.

```sql
-- Beyond requirement (3), an added test: postings whose line belongs to another invoice
-- Population: the 9,525 postings above; expected: no rows
SELECT gl.GLEntryID, gl.SourceDocumentID, gl.SourceLineID,
    sil.SalesInvoiceID
FROM GLEntry AS gl
    INNER JOIN SalesInvoiceLine AS sil
        ON sil.SalesInvoiceLineID = gl.SourceLineID
WHERE gl.SourceDocumentType = 'SalesInvoice'
    AND gl.FiscalYear = 2026
    AND sil.SalesInvoiceID <> gl.SourceDocumentID;
```

**Step 9. List the accounts of the postings that have no SourceLineID.** A hint, beyond the exercise.

```sql
-- Requirement (3): the accounts of the postings with no SourceLineID
-- Population: GLEntry, SalesInvoice, fiscal 2026; expected: 1020, 2050 and 4050
SELECT a.AccountNumber, a.AccountName, COUNT(*) AS Postings
FROM GLEntry AS gl
    INNER JOIN Account AS a ON a.AccountID = gl.AccountID
WHERE gl.SourceDocumentType = 'SalesInvoice'
    AND gl.FiscalYear = 2026
    AND gl.SourceLineID IS NULL
GROUP BY a.AccountID, a.AccountNumber, a.AccountName
ORDER BY a.AccountNumber;
```

**Check:** {{ tested|count }} postings tested and no exception; Steps 7 and 8 return no rows, and Step 9 shows the three header-level accounts, {{ g.header_accounts|join(', ') }}, with {{ g.header|count }} postings in all. **Watch for:** without the SourceLineID test, the anti-join returns {{ g.anti_all|count }} rows, the header-level postings, which have no line by design. Without the document type it returns {{ g.anti_types|count }}, the line IDs of other documents' tables. An INNER JOIN returns {{ g.inner|count }} rows, the postings tested, which a rushed student reads as exceptions.

## What a strong answer says

- **Requirement (1).** The debit records the receivable for the GrandTotal; the credits record the revenue (the SubTotal), the freight billed and the sales tax owed. They balance. The join names the type because each document table numbers its own rows.
- **Requirement (4).** Every posting records its document: SourceDocumentType names the table, SourceDocumentID the document, SourceLineID the line. Joined on those columns, an auditor moves from the ledger to the document, vouching; read the other way, the same keys find every posting a document made, tracing. Requirement (3) shows that every tested posting, each SalesInvoice posting of the year with a SourceLineID, points to an existing invoice line. It does not show that the line belongs to the invoice in SourceDocumentID, which the added test of Step 8 checks, or that every invoice line was posted, which is the test in the other direction, or that the amounts agree, or that the documents are genuine. A memo that reports the ownership test as an extra step is a plus.

A weak memo says that the ledger is complete because the anti-join found nothing, claims from the anti-join alone that each line belongs to its invoice, or does not say which direction the test runs.

## Common mistakes and how to respond

- **The ID alone in the join to the ledger.** *Symptom:* {{ trap_rows }} rows. *Response:* ask which table an ID of {{ inv.id }} belongs to in each row.
- **The invoice ID used to reach the line.** *Symptom:* {{ g.line_by_invoice }} rows where one is expected. *Response:* ask which column names the line.
- **An anti-join with no IS NOT NULL test.** *Symptom:* {{ g.anti_all|count }} exceptions. *Response:* ask what a NULL SourceLineID means.
- **An anti-join with no document type.** *Symptom:* {{ g.anti_types|count }} exceptions. *Response:* ask which table those line IDs belong to.
- **An inner join as the exception test.** *Symptom:* {{ g.inner|count }} rows reported as exceptions. *Response:* ask what the join keeps.
- **An empty result read as proof.** *Symptom:* a memo that calls the ledger complete. *Response:* ask which direction the test runs.
- **Ownership read from the anti-join.** *Symptom:* a memo that says each line belongs to the invoice the posting names. *Response:* ask which columns the anti-join compares, and what a line of another invoice would return.

## Extensions and discussion questions

- Run the reverse test. A NOT EXISTS from SalesInvoiceLine that names SourceDocumentType, SourceDocumentID and SourceLineID of the ledger uses the ledger's index, and returns {{ g.reverse }} rows: every invoice line has a revenue posting. Ask why all three columns belong in the test.
- Extend the trace to the order, shipment and receipt, as Tutorial 3.2 did.
- Discuss: an empty anti-join is a result; what would convince you that the test could have found something?
- Discuss: which of the four documents of this trace would you test next in a year-end audit, and in which direction?
